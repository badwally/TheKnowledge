# Using Berlin SPARQL benchmark to evaluate virtual SPARQL endpoints over relational databases

## Abstract

The RDF is a popular and well-documented format for publishing structured data on the web. It enables data to be consumed without the knowledge of how the data is internally stored. There are already several native RDF storage solutions that provide a SPARQL endpoint. However, native RDF stores are not widely adopted. It is still more common to store data in a [relational database](https://www.sciencedirect.com/topics/computer-science/relational-database). One of the useful features of native RDF storage solutions is providing a SPARQL endpoint, a web service to query RDF data with SPARQL. To provide this feature also on top of prevalent relational databases, solutions for virtual SPARQL endpoints on top of a [relational database](https://www.sciencedirect.com/topics/earth-and-planetary-sciences/relational-database) have appeared. To benchmark these solutions, a state-of-the-art tool, the Berlin SPARQL Benchmark (BSBM), is used. However, BSBM was designed primarily to benchmark native RDF stores. It can also be used to benchmark solutions for virtual SPARQL endpoints. However, since BSBM was not designed for virtual SPARQL endpoints, each implementation uses that tool differently for evaluation. As a result, the evaluation is not consistent and therefore hardly comparable. In this paper, we demonstrate how this well-defined benchmarking tool for SPARQL endpoints can be used to evaluate virtual endpoints over relational databases, perform the evaluation on the available implementations, and provide instructions on how to repeat the same evaluation in the future.

## Introduction

The RDF \[1\], \[2\] is a well-documented and popular format for publishing structured data on the web. It enables data to be consumed without the knowledge of how the data is internally stored. Moreover, it supports the evolution of schemas without requiring changes in services which consume the data. One of the features is the ability to provide a web service which consumers can then use to query the data using SPARQL language \[3\], the so-called “SPARQL endpoint”.

There are already several native RDF storage solutions that provide a SPARQL endpoint. However, they are not widely adopted. It is still more common to store data in relational databases. For example, the top 4 database engines in the ranking of database engines1 are primarily relational. There is no database engine with native RDF support in the top 50 engines.

Lately, there is also a new motivation for representing a relational database in the form of knowledge graphs. It seems that Large Language Models perform way better on top of knowledge graph representation of the relational databases than when using the relational database directly \[4\].

There is a difference between how data is usually stored and how it should ideally be published. There have been various attempts to close this gap. A W3C Working Group has been established2 to find a solution. The group has produced several standards \[5\], \[6\] that specify the transformation of relational data to an RDF representation.

However, it requires either a separate data store for the application and the published data or migration of the application to use the RDF data store. This is not always possible, as various platforms are coupled to a specific data store. For example, the major3 CMS platform WordPress4 and the major5 e-commerce platforms WooCommerce6 and Shopify7 are based on the MySQL relational database.

Therefore, the transformation of relational data may not always be a possible nor an ideal solution. Especially, when a SPARQL endpoint is needed, it requires to load the transformed data into an RDF storage. It means an unnecessary cost to maintain two data stores and to maintain the freshness of the data in the RDF copy.

For systems where the data are primarily stored in a relational database, it would be ideal to build a SPARQL endpoint directly over a relational database, the so-called virtual SPARQL endpoint. The virtual SPARQL endpoint does not query the materialized RDF data, instead it transforms the input SPARQL query into one or more relational queries, which are used to retrieve the necessary data from the relational database. The retrieved data are then transformed into the expected RDF form like if the query was performed over the materialized RDF data. It allows customers to treat the underlying relational database as if it were a native RDF storage without the need to store the dataset in two data stores and synchronize them. There are already several implementations of virtual SPARQL endpoints over relational databases and these have been used to build knowledge graphs over relational databases \[7\], \[8\], \[9\].

However, there is no benchmark that specializes in virtual SPARQL endpoints, which means that consistent evaluations are lacking. Moreover, it is not straightforward to use, as it is necessary to first define the mapping between the relational database and adjust the benchmark to work well with the mapped RDF representation. Therefore, while the authors of existing implementations of virtual SPARQL endpoints have already used the existing SPARQL benchmark to generate the relational dataset, there is no documentation of how the evaluation was done. Therefore, the evaluations are neither reproducible nor repeatable. Furthermore, since the benchmarking tool is not used to run a large number of random queries for the evaluation, the solutions can perform optimizations that skew the evaluation results, although the optimizations are not applicable in a real environment. Such an approach is not objective and is easily tailored to suit one of the solutions the most.

In this paper, we use the Berlin SPARQL Benchmark \[10\], \[11\] to evaluate existing approaches to a virtual SPARQL endpoint over a relational database. In particular, the paper has the following contributions:

- •
We define aspects that are used to evaluate a virtual SPARQL endpoint solution.

- •
We update the existing SPARQL benchmark to support the evaluation of the virtual SPARQL endpoint out of the box.

- •
We define the evaluation approach based on the benchmark.

- •
We evaluate existing virtual SPARQL endpoint solutions.

- •
We provide all the information, scripts, and tools necessary to reproduce the results and repeat the evaluation in the future.


In the following sections, we provide some background information on the virtual SPARQL endpoints. In Section 2, we explain how a mapping from a relational database to an RDF dataset can be defined to describe the link between a virtual SPARQL endpoint and its underlying relational database. In Section 3 we list the related work: both virtual SPARQL endpoint implementations and available benchmarks.

Then, in Section 4, we describe the Berlin SPARQL Benchmark in better detail, describe why it cannot be used out of the box for virtual SPARQL endpoints, and then describe the necessary modifications. This is used in Section 5, where we define the aspects for evaluating a virtual SPARQL endpoint using this modified tool. We do not focus only on the performance, but also include other aspects like usability and soundness to identify the weak spots of the implementations. For performance benchmarking, we provide scripting to orchestrate the benchmark to ensure that the results are reproducible and, more importantly, repeatable in the future to evaluate available solutions in the future. We perform an evaluation of existing virtual SPARQL endpoints using the defined aspects. Moreover, we do not only look at the evaluation results, but we also dive deep and describe why the solutions achieved such a result.

## Conclusion

In this paper, we have described the evaluation of virtual SPARQL endpoints using Berlin SPARQL Benchmark tools. We have shown how the tools can be used to evaluate virtual SPARQL endpoint solutions and what the gaps of the benchmark are from that perspective. We have provided patches for these gaps. Moreover, we have provided scripting to orchestrate the benchmark to ensure that the results are reproducible and, more importantly, repeatable in the future to evaluate available solutions.
