Dolby Experience Management Prototype Platform (DxMP)
Prototype Requirements
DRAFT version 0.5
18 February 2020
For use in initial discussion
Overview:
This document outlines first the basic proposed requirements for the next phase of the CEG
Cloud experience demo. This demo is meant to represent the lightest expression of the overall
Dolby Experience Management (DxM) concept: A device asserts what it is and a bit of
information about its environment, and the system delivers assets optimized for that context
using XCD. The result is a more cost-effective system for delivering the best possible experience
to a given context, as measured by realized quality of experience.

What the Phase One Prototype will do:
This prototype has three components: a PLAYBACK system, an ENCODING system, and an
Experience Analysis system.
These components are intended to represent the lightest expression of the overall DxM
concept: A device asserts what it is and a bit of information about its environment, and the
system delivers assets optimized for that context using XCD. The result is a more cost-effective
system for delivering the best possible experience to a given context, as measured by realized
quality of experience.
The Playback System:
The playback system has some combination of 3 source devices and 3 sink devices.
Characteristics of each source and sink device will be stored in a device database.
Players for each device application will include a beacon system that queries the buffer state,
records player events, and transmits that data to the QoE system.
A player will attest to a system of its identity when establishing a session.
At the same time, the application will query the identity of any downstream SINK device
connected over HDMI.
The player will also query the Microphone and the Camera to determine the noise and light in a
room, reduced to values that basically correspond to L, M, H.
The player will use these coordinate values (Native device, HDMI device, Audible Environmental
information, Visual Environmental information) to request the correct pre-coded asset with
corresponding encoder parameters (including ABR ladder).
The playback system will fetch the correct pre-coded processed asset from the Origin library
and deliver that to the player application on the device.
The system will play this asset back, with no local post-processing.

The Encoding System:
The Encoding System – preferably built on top of Hybrik – will source mezzanine assets from an
mezzanine library (e.g. an S3 bucket) and encode variants of that content that correspond with
every possible combination of the source device, sink device, environmental noise, and
environmental light.
Given 3 source types, 3 sink types, 3 possible environmental noise values, and 3 possible
environmental light values, the maximum number of encoding variants is 81 (3^4).
We should also assume 5 rungs to every ABR ladder.
So, there are a total of 405 variants of any asset at varying chunk sizes.
The encoding system will create the appropriate manifests for every combination and store
that in an origin library (a different S3 bucket) for ingest onto a CDN for delivery.

represent the potential values for LIGHT and NOISE for an example device – the LG C6 SMART

QoE System:
At the time of ingest, the ENCODING system will also assign “QoE” values to the source content,
and the relative MAX QoE value for the requesting Source-Sink combination (see FLOW below).
The QoE system ingests network and player events from the Player Beacon.

At the end of a session, the QoE system will report the possible QoE for the session and the
realized QoE.
The system will also use fixed inputs on CDN pricing to calculate the cost of the session both
absolutely and relative to what the cost would have been had no optimization occurred.
The system requires a Quality of Experience process that derives a maximum QoE value
(MAXQ) for the mezzanine asset and then calculates the weighted MAX value of REALQ based
on Network conditions and Device Capability. For both MAXQ and REALQ, the value is the SUM
of AUDQ and VIDQ.
Let’s make up an example that will not stand to scrutiny, but give you an idea of what I’m
aiming at:
• Let’s assume that our Origin source is a Dolby Atmos/Dolby Vision mezzanine
file.
• Atmos/Vision mezzanine asset may have a possible QoE of 2 (Audio=1, Video=1).
We will call this SOURCEQ
• However, an SDR TV brings the Max VIDQ to a lower level based on the
resolution and peak luminance of the screen; in this example, let’s assume a
MAX VIDQ for this TV of .5.
• Given connectivity to a downstream Atmos Soundbar over HDMI, the MAX
AUDQ is .8.
• The devices are in a DARK room; therefore the MAX ENVVIDQ is .9.
• The devices are in a QUIET room; therefore the MAX ENVAUDQ is .9.
• In this model, we assume that the value of audio and video on QOE is equal.
• So, the MAX REALQ for the session is SUM[(MAXAUDQ*MAX ENVVIDQ),
(MAXVIDQ*MAX ENVAUDQ)= 1.17
• As the asset moves down the ABR ladder, the REAL Q declines proportionately.
For an ABR ladder with two rungs, one at ABR10Mbps and the other at
ABR1Mbps, and assuming that there is a straight line relationship between
changes in both audio and video bitrate, the REAL Q at ABR1 is (1.17*.1) or
.{.117}; at ABR2 the value is {1.17} – that is, you get everything possible out of
the combination of DEVICE and ENVIRONMENT.

• So, a session that sticks to the lowest rung on the ABR ladder realizes 6% of the
possible QoE of the SOURCEQ. It realized 10% of the MAX REAL Q of 1.17.
• Apply XCD and half the video session is able to hit the top rung for both AUD and
VID. So, the is (.117*.5)+(1.17*.5) or 0.32; it realized 28% of the MAX REAL Q of
1.17

down.

EXAMPLE FLOW:
1. A content library is accessed via UI on a PLAYER APPLICATION.
2. The APPLICATION prompts the user to “CALIBRATE THE EXPERIENCE?” with a single button.
3. When pressed, the button activates a CALL to SENSOR APIs on the DEVICE.
o Values of LIGHT (from camera) and NOISE LEVELS (from microphone) are obtained
and applied to a local rule set within the application to determine the
ENVIRONMENT of the room.
• Values of LIGHT are either (DARK, MEDIUM, LIGHT) based on some range of
discrete values from the sensor.
• Values of NOISE are either (QUIET, NORMAL, LOUD) based on some range of
discrete values from the microphone.
4. USER Validates they are in (e.g.) “A Dark, Loud Room. Is this correct?”
• Values of HDMI CONNECTIVITY are obtained by assessing the HDMI STATE
(Connected Y/N) and the AUDIO and VIDEO capability of the SINK device by querying
the HDMI DEVICE, SHORT AUDIO DESCRIPTOR and the SHORT VIDEO DESCRIPTOR.
• Values correspond with a DEVICE in the DEVICEDB and are used to amend the
URL and select the correct MANIFEST from the CMS.
5. The values of the downstream device are used to inform via URL the upstream system of
the correct MANIFEST associated with the asset.
6. USER selects ASSET from UI and presses PLAY, a URL is created with the amended query
parameters corresponding to the LIGHT and NOISE levels in the room.
7. The URL corresponds to the MANIFEST FILE associated with the PRECODED version of the
ASSET for the combination of (DEVICE, HDMI, LIGHT, NOISE).
8. Using XCD, the player will achieve the highest run on the ABR ladder corresponding to the
correct combination of DEVICE and ENVIRONMENT.
9. At the conclusion of the trailer, the UI will surface to the user the QoE score for the session,
thecost of the stream if no optimization had occurred, the cost using the optimized system,
and the % of savings and the absolute value of the savings assuming 1MN similar sessions.

A Draft Vision for the Dolby Experience Management Platform (DxM):
The Dolby Experience Management Platform (DxM) enables media companies of any size to
create and manage efficient delivery of personalized experiences at scale. DxM users receive
guidance about or automate the best potential action or most profitable action at any point in
the experience creation and delivery lifecycle. Using DxM, media companies can measure the
business value of sensational entertainment experiences across the entire delivery lifecycle
through the use of data analysis and machine learning. With DxM, media companies identify
and deliver the highest value experiences to a given user at the lowest possible aggregate cost.
DxM identifies the entire context of a entertainment experience, including technical content
attributes, network metadata, device capabilities, and user and environmental detail. By
providing this context on an individual or segment basis in near real-time across every data-
defined behavior and event along the lifecycle, DxM allows MediaCos to make decisions,
diagnose issues, and automate responses based on the next best action applied to a piece of
content, an audience segment, a target device, or a delivery network. The system analyzes
transactions in the context of quality of experience across time duration, content provisioning
decisions, and network and player events to quantify the holistic cost and impact of a given
experience.
