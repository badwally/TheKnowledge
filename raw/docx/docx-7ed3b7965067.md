# Competitive Intelligence Agent — Specification

Status: Draft — requires CMO input on Sections 3.2, 4.2, 5.3 Related workflows: 0.1 (Competitive landscape monitoring), 9.5 (Competitive positioning refresh), A.11 (Competitor AEO tracking) Escalation level: Level 0 (cron + structured prompts). Graduates to Level 1 if RAG corpus justifies persistent shared state. Architecture target: Dedicated research agent with MCP connectors and RAG over accumulated intelligence corpus.

## 1. Purpose

This agent replaces ad-hoc, manual competitive monitoring with a systematic, scheduled intelligence function. It scans defined sources on a cron cadence, extracts and classifies competitive signals, scores them against weighted analytical criteria, assembles a digest at a defined cadence, and recommends actions — including “do nothing” — with reasoning the CMO can audit and override.

The agent’s output is not a news feed. It is an analytical product: signals are filtered, deduplicated, weighted, and presented with context and recommended responses. The weighting framework is the core intellectual property of this spec; getting it right requires CMO collaboration.

## 2. Source Taxonomy

Sources are classified along two independent axes: provenance (where the signal originates) and access pattern (how the agent retrieves it).

### 2.1 Provenance Taxonomy

Faceted, MECE at each level. Every source maps to exactly one provenance category.

S1  Competitor Direct Channels
    S1.1  Website content (landing pages, pricing, feature pages, case studies)
    S1.2  Blog / changelog / release notes
    S1.3  Press releases and newsroom
    S1.4  Job postings (engineering, marketing, sales, leadership)
    S1.5  Social accounts (LinkedIn company page, X/Twitter, YouTube)

S2  Platform and Marketplace Signals
    S2.1  Klaviyo marketplace listings (new apps, updated descriptions, reviews)
    S2.2  Shopify App Store (competitor listings, ratings, install counts)
    S2.3  G2 / Capterra / TrustRadius (reviews, category rankings, feature comparisons)
    S2.4  Product Hunt (new launches, upvotes)

S3  Industry and Market Sources
    S3.1  Analyst reports (Gartner, Forrester, custom research)
    S3.2  Industry publications (Martech Record, Practical Ecommerce, etc.)
    S3.3  Conference announcements and speaker lists
    S3.4  Regulatory and compliance developments (CAN-SPAM, GDPR enforcement actions)

S4  Community and Social Signals
    S4.1  Reddit (r/ecommerce, r/klaviyo, r/emailmarketing, r/saas)
    S4.2  Slack communities (ecommerce-focused, Klaviyo partner channels)
    S4.3  LinkedIn individual posts from competitor executives and employees
    S4.4  X/Twitter keyword monitoring

S5  Financial and Organizational Signals
    S5.1  Crunchbase / PitchBook (funding rounds, acquisitions, investor activity)
    S5.2  SEC filings (for public competitors)
    S5.3  Patent filings (USPTO, Google Patents)

S6  Technical and Open Source Signals
    S6.1  GitHub repositories (new repos, release activity, contributor patterns)
    S6.2  npm / PyPI package publications
    S6.3  Technical blog posts and architecture disclosures
    S6.4  API documentation changes (new endpoints, deprecations)

S7  Ecosystem and Partner Signals
    S7.1  Integration announcements (new ESP connectors, CRM integrations)
    S7.2  Agency partner program changes
    S7.3  Crossbeam overlap shifts (requires Crossbeam integration)
    S7.4  PartnerStack competitive referral patterns (requires PartnerStack integration)

### 2.3 Source Reliability Scores (Defaults)

Each source type carries a default reliability score reflecting historical accuracy of claims from that provenance. These are starting values; the agent should track confirmation rates and adjust over time.

| Source Type | Default Reliability | Rationale |
| --- | --- | --- |
| Competitor press release / changelog | 0.95 | First-party, verified by publisher |
| Earnings call transcript | 0.90 | Regulated disclosure |
| Job posting | 0.85 | Reflects intent; may not reflect execution |
| G2/Capterra review | 0.75 | Verified user, but subjective and potentially incentivized |
| Industry analyst report | 0.80 | Professional analysis; may lag reality |
| LinkedIn post (executive) | 0.70 | First-party but promotional framing |
| Reddit/community discussion | 0.50 | Unverified; useful for sentiment, unreliable for facts |
| X/Twitter | 0.40 | High noise ratio; useful for speed of detection |
| Speculative inference (pattern-based) | 0.30 | Agent’s own extrapolation; flag explicitly |

[CMO INPUT REQUIRED] Validate these defaults. Adjust based on Orita’s experience with each source type. Some sources may be systematically more or less reliable in the email deliverability vertical than these general defaults suggest.

## 3. Signal Category Ontology

### 3.1 Signal Facets

Signals are classified using four independent facets. Each facet uses a controlled vocabulary — no free text in category fields.

Facet 1: Signal Category (what happened)

| Code | Category | Definition | Examples |
| --- | --- | --- | --- |
| PRODUCT | Product / Feature | New capability, feature change, deprecation, technical architecture shift | New AI feature launch, API deprecation, platform expansion |
| PRICING | Pricing / Packaging | Price change, plan restructuring, new tier, discount program | Free tier added, enterprise pricing increase, usage-based shift |
| GTM | Go-to-Market | Messaging change, channel strategy, campaign, event presence | New positioning claim, agency program launch, conference sponsorship |
| TALENT | Personnel / Organization | Hiring patterns, executive moves, team restructuring, layoffs | VP Engineering hire, CTO departure, engineering team expansion |
| FINANCE | Financial / Corporate | Funding, acquisition, revenue disclosure, partnership | Series B raise, acquisition of adjacent company, IPO filing |
| ECOSYSTEM | Ecosystem / Integration | New integration, partner program change, marketplace activity | Klaviyo app update, new ESP connector, agency partner tier change |
| CONTENT | Content / Positioning | Published content that signals strategic direction | Whitepaper on new vertical, case study in adjacent market, AEO-optimized content |
| MARKET | Market / Regulatory | Industry trend, regulatory change, market shift | New CAN-SPAM enforcement, ESP market consolidation, AI regulation |

Facet 2: Strategic Relevance (who does this affect)

| Code | Definition |
| --- | --- |
| DIRECT | Direct competitor in email deliverability / audience intelligence |
| ADJACENT | Company in adjacent space (ESP, CRM, enrichment) whose move affects Orita’s market |
| ECOSYSTEM | Klaviyo ecosystem player (agency, app, integration partner) |
| MARKET | Industry-wide trend or regulatory shift |

Facet 3: Impact Domain (what it threatens or enables)

| Code | Definition |
| --- | --- |
| FEATURE_PARITY | Competitor closing a capability gap or opening a new one |
| MARKET_SHARE | Direct threat to or opportunity for customer acquisition |
| PRICING_PRESSURE | Affects Orita’s pricing power or value perception |
| CHANNEL_THREAT | Threatens Orita’s distribution (agency partners, Klaviyo relationship) |
| POSITIONING | Affects Orita’s narrative or category definition |
| EXPANSION | Relevant to Orita’s growth vectors (SMS, direct mail, new ESPs, AEO) |

Facet 4: Temporal Horizon

| Code | Definition |
| --- | --- |
| IMMEDIATE | Requires attention within days. Customer-facing impact possible now. |
| NEAR_TERM | Relevant within 30-90 days. Strategic adjustment window. |
| STRATEGIC | 3-12 month horizon. Informs planning, not action. |
| TREND | Ongoing pattern. No discrete event; accumulating signal. |

## 4. Weighting Framework

### 4.1 Composite Signal Score

Every signal receives a composite score from three independent dimensions, each scored 0.0-1.0:

Confidence = How much should we trust this signal?

confidence = (source_reliability × 0.6) + (corroboration_score × 0.4)

where:
  source_reliability = default from Section 2.3, adjusted by track record
  corroboration_score:
    single source, no corroboration     = 0.3
    single source, consistent with trend = 0.5
    two independent sources              = 0.7
    three+ independent sources           = 0.9
    first-party + third-party confirm    = 1.0

Impact = How much does this matter to Orita?

impact = severity_base × relevance_multiplier

where:
  severity_base (from signal content):
    existential threat or major opportunity  = 1.0
    significant competitive shift            = 0.7
    moderate positioning change              = 0.4
    minor or incremental change              = 0.2

  relevance_multiplier (from competitor priority):
    HIGH priority competitor   = 1.0
    MEDIUM priority competitor = 0.7
    LOW priority competitor    = 0.4
    MARKET (no specific competitor) = 0.5

Urgency = How quickly does this need attention?

IMMEDIATE   = 1.0
  NEAR_TERM   = 0.7
  STRATEGIC   = 0.4
  TREND       = 0.2

Composite score = confidence × 0.3 + impact × 0.5 + urgency × 0.2

Impact is weighted highest because the CMO’s scarce resource is attention. A high-confidence, low-impact signal should not crowd out a moderate-confidence, high-impact one.

### 4.2 Weighting Criteria — CMO Calibration Required

[CMO INPUT REQUIRED] The dimension weights (0.3 / 0.5 / 0.2) and severity definitions need calibration against real examples. Proposed calibration exercise:

Collect 10-15 competitive events from the past 12 months that the CMO remembers (mix of consequential and noise).

Have the CMO rank them by “how much attention did this deserve?”

Score each using the framework above.

Compare framework ranking to CMO ranking.

Adjust weights until the framework reproduces the CMO’s judgment on historical data.

This is 1-2 hours of structured conversation. It produces calibrated weights and a set of scored reference examples the agent can use as few-shot examples in its analysis prompt.

### 4.3 Temporal Decay

Signals lose relevance over time unless refreshed by new corroborating evidence.

decayed_score = composite_score × decay_factor

where:
  decay_factor = 0.5 ^ (days_since_detection / half_life)

  half_life by temporal horizon:
    IMMEDIATE  = 14 days
    NEAR_TERM  = 45 days
    STRATEGIC  = 120 days
    TREND      = 365 days (slow decay; trends persist)

Signals below a threshold score (default: 0.15) after decay are archived and excluded from digests.

## 5. Action Recommendation Taxonomy

### 5.1 Action Types

Every signal in the digest includes a recommended action from this controlled vocabulary:

| Action | Definition | Typical trigger |
| --- | --- | --- |
| MONITOR | No action needed. Continue watching. | Low-impact or low-confidence signal |
| BRIEF_TEAM | Share with relevant internal stakeholders. | Moderate impact; awareness needed, no response yet |
| ADJUST_MESSAGING | Update sales collateral, positioning, or competitive battlecards | Competitor messaging shift or feature claim affecting Orita’s narrative |
| ACCELERATE_ROADMAP | Recommend prioritizing a planned capability | Competitor closing a gap Orita planned to maintain |
| EVALUATE_RESPONSE | Requires deeper analysis before choosing action | High-impact signal with insufficient data for a specific recommendation |
| ENGAGE_PARTNERS | Notify or coordinate with agency partners or Klaviyo | Ecosystem shift affecting partner relationships |
| CONTENT_RESPONSE | Publish content addressing the competitive development | Competitor content gaining traction in Orita’s category queries |
| DO_NOTHING | Assessed and explicitly dismissed. Reasoning documented. | Signal is noise, irrelevant, or already accounted for |

### 5.2 Recommendation Logic

The agent maps composite score and facet combination to recommended actions:

if composite_score < 0.25:
    action = DO_NOTHING

elif composite_score < 0.40:
    action = MONITOR

elif composite_score < 0.60:
    if impact_domain in [FEATURE_PARITY, PRICING_PRESSURE]:
        action = BRIEF_TEAM
    elif impact_domain == POSITIONING:
        action = CONTENT_RESPONSE
    else:
        action = MONITOR

elif composite_score < 0.80:
    if impact_domain == FEATURE_PARITY:
        action = ACCELERATE_ROADMAP
    elif impact_domain == POSITIONING:
        action = ADJUST_MESSAGING
    elif impact_domain == CHANNEL_THREAT:
        action = ENGAGE_PARTNERS
    else:
        action = EVALUATE_RESPONSE

else:  # composite_score >= 0.80
    action = EVALUATE_RESPONSE  # high-impact signals always get human judgment

The agent explains its reasoning for each recommendation. The CMO overrides freely; overrides are logged and fed back to improve future recommendations.

### 5.3 Override Feedback Loop

[CMO INPUT REQUIRED] Define the override mechanism. Options:

Slack reaction: CMO reacts to digest items with predefined emoji to confirm or override the recommendation.

Structured reply: CMO replies with a corrected action code and optional note.

Weekly review session: Batch review of the week’s signals with corrections applied retroactively.

Overrides accumulate as training data. After 50+ overrides, re-run the calibration exercise (Section 4.2) to update weights.

## 6. Digest Format and Cadence

### 6.1 Cadence

| Digest Type | Frequency | Content | Delivery |
| --- | --- | --- | --- |
| Daily scan | Every morning (cron) | New signals detected in last 24 hours, scored and categorized | Slack channel or email |
| Weekly intelligence brief | Monday morning | Aggregated view: top signals by composite score, trend analysis, action items carried forward | Slack + document (Google Doc or Notion) |
| Monthly strategic review | First week of month | Competitor positioning changes over 30 days, emerging trends, effectiveness of past responses, weight recalibration notes | Document for CMO review |

### 6.2 Daily Digest Structure

COMPETITIVE INTELLIGENCE DIGEST — [DATE]

SIGNALS REQUIRING ATTENTION (composite score >= 0.60)
  [Signal title]
  Source: [provenance] | Confidence: [score] | Impact: [score] | Urgency: [horizon]
  Summary: [2-3 sentences]
  Recommended action: [ACTION_TYPE] — [reasoning]

MONITORING (composite score 0.25-0.59)
  [Signal title] — [one-line summary] — [ACTION_TYPE]
  ...

DISMISSED (composite score < 0.25)
  [count] signals assessed and dismissed. [link to full log]

TRENDS
  [Any accumulating patterns across multiple signals]

### 6.3 Intelligence Corpus (RAG Foundation)

All signals — including dismissed ones — persist in a structured corpus. This corpus serves as:

RAG retrieval base for the agent’s analysis prompts (historical context improves classification accuracy)

Trend detection substrate (patterns emerge from accumulated low-confidence signals)

Calibration dataset (CMO overrides + confirmed assessments train the weighting model)

Institutional memory (what did Competitor X do 6 months ago before their last product launch?)

Corpus schema per record:

signal_id:          UUID
detected_date:      ISO 8601
event_date:         ISO 8601 (if known; null if inferred from detection)
title:              string
summary:            string (2-3 sentences)
raw_source_url:     string
source_provenance:  S-code from Section 2.1
source_reliability: float (0.0-1.0)
facets:
  category:         PRODUCT | PRICING | GTM | TALENT | FINANCE | ECOSYSTEM | CONTENT | MARKET
  relevance:        DIRECT | ADJACENT | ECOSYSTEM | MARKET
  impact_domain:    FEATURE_PARITY | MARKET_SHARE | PRICING_PRESSURE | CHANNEL_THREAT | POSITIONING | EXPANSION
  temporal_horizon: IMMEDIATE | NEAR_TERM | STRATEGIC | TREND
competitor:         string (from registry) or null
confidence_score:   float (0.0-1.0)
impact_score:       float (0.0-1.0)
urgency_score:      float (0.0-1.0)
composite_score:    float (0.0-1.0)
recommended_action: ACTION_TYPE
action_reasoning:   string
cmo_override:       ACTION_TYPE or null
cmo_override_note:  string or null
status:             ACTIVE | WATCHING | RESOLVED | SUPERSEDED | ARCHIVED
related_signals:    [signal_id, ...]

Storage: JSON lines, SQLite, or Postgres — determined at implementation. The schema is the contract; storage is an implementation detail.

## 7. Agent Architecture

### 7.1 Runtime Model

[Cron trigger] → [Source Scanner] → [Signal Extractor] → [Classifier/Scorer] → [Digest Assembler] → [Delivery]
                                                                ↑                        ↑
                                                          [RAG Corpus]            [CMO Overrides]

Each stage is a discrete prompt or function call, not a monolithic process. This supports independent iteration on any stage without rewriting the pipeline.

### 7.2 MCP and Tool Requirements

| Component | Tool / MCP | Purpose |
| --- | --- | --- |
| Web scanning | WebSearch, WebFetch | Periodic scraping of competitor sites, search queries |
| RSS ingestion | RSS parser (custom or library) | Monitor changelog/blog feeds |
| GitHub monitoring | GitHub API | Track repos, releases, contributor activity |
| Crunchbase/funding | Crunchbase API or web scrape | Financial signals |
| G2/review platforms | G2 API or periodic scrape | Review monitoring, category ranking changes |
| Slack delivery | Slack MCP | Digest delivery, override collection |
| Google Docs/Notion | Google Drive MCP or Notion MCP | Weekly/monthly brief storage |
| Corpus storage | Local file system or database | RAG retrieval base |
| RAG retrieval | Embedding model + vector search (or structured query) | Historical context for classification |

### 7.3 Prompt Architecture

The agent uses separate prompts for each pipeline stage:

Scan prompt: Given [source list + access instructions], retrieve new content since [last scan timestamp]. Output: raw signal candidates.

Classification prompt: Given [raw signal + facet definitions + competitor registry], assign facets. Output: classified signal record.

Scoring prompt: Given [classified signal + weighting framework + reference examples from calibration], compute confidence/impact/urgency scores and composite. Output: scored signal.

Recommendation prompt: Given [scored signal + action taxonomy + recent CMO overrides on similar signals], recommend action with reasoning. Output: signal with recommendation.

Digest prompt: Given [all signals from this cycle, sorted by composite score], assemble formatted digest. Output: digest text.

Each prompt receives the controlled vocabularies and scoring rules as system context. Few-shot examples from the CMO calibration exercise (Section 4.2) anchor the scoring prompts.

## 10. Implementation Notes

Escalation level: Level 0 at launch. Cron trigger, structured prompts, formatted output. No cross-workflow dependencies required for v1.

RAG graduation: Once the corpus accumulates 200+ signals (approximately 2-3 months of operation), evaluate whether RAG retrieval measurably improves classification accuracy versus the baseline prompt with few-shot examples only. If yes, add embedding + retrieval as a pipeline stage (graduates to Level 1: shared persistent state).

Build estimate: Source scanner + classifier + scorer + digest assembler = 4 discrete prompts + a cron job + Slack delivery. Scaffolding: one afternoon. Prompt tuning to acceptable quality: 1-2 days, gated by CMO calibration session. RAG layer: separate build, deferred.

What this spec does not cover: The implementation details of the RAG system (embedding model selection, vector store, chunking strategy, retrieval parameters). Those are implementation decisions that depend on corpus characteristics observed after the agent has been running. Specify them when the data justifies the investment.
