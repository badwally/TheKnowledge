1. CORE INVARIANT — single serialization point for writes, not a single process. What must be singular is the linearization of commits to canonical state, not the number of librarian instances. Concurrency model is optimistic / MVCC: research, authorship, validation, and dedup-similarity run concurrently against a corpus snapshot; only the commit is serial. Topology: N librarian workers, one commit gate (a dedicated committer or a commit mutex — DEFERRED, §15). Reject multiple independent committers: concurrent writers to one branch corrupt the git index (`.git/index.lock` already serializes git itself), and partitioned committers cannot enforce global invariants (dedup, contradiction) that span domains. The serial gate is the throughput ceiling by design; do NOT assert it is "sub-second" or "never a bottleneck" — require it to be measured (§16, ledger). Reads are non-blocking against committed snapshots: specify that runtime reads resolve at a git ref/commit (atomic snapshot) rather than the live working tree, which can be mid-multi-file-write.

2. INTEGRITY BOUNDARY (corrected) — there is NO single transaction across the three stores (markdown working tree, FTS5/embedding index, git object store). Do not claim "single logical transaction" or "database-grade integrity." The only atomic primitive is `git commit`. The honest model: markdown is canonical; the index is derived, rebuildable, and never on the integrity-critical path; git is the atomic commit boundary. Specify commit ordering (markdown write → git commit → index update) and a crash-recovery procedure at each step boundary. Note that committing-per-intent is NEW behavior — today only `discharge_orphans.py` shells git; the write path does not commit — flag it as a migration delta, not an extension.

3. LIBRARIAN MODEL & THE DEPOSIT API — agents are producers of intent. An intent is a declarative, immutable, addressable record of what an agent wants to become true in the corpus, submitted to the librarian and enacted by it. Agents never write the tree, never commit, never resolve conflicts. The intent is also a CALLABLE API, not just a data structure — specify: the deposit tool's MCP signature; a content-addressed `intent_id` (hash over payload + originating identity + intent semantics) serving as idempotency key; the synchronous return (accepted/queued status + `intent_id`, NOT paths-touched, since commit is async); a status-query op that maps `intent_id` → terminal disposition (committed→path | merged→canonical-path | rejected→rule | quarantined→queue | dead-lettered→reason); and how this reconciles with the existing `OperationResult` shape. Specify the intent lifecycle state machine: `submitted → claimed(worker, lease) → authored → committed | rejected | dead-lettered`, with durable enqueue-before-ack, a visibility lease so a crashed worker's intent is reclaimed, max-retry → dead-letter, and the restart recovery scan. Each intent carries originating agent/project/session identity (self-declared and unauthenticated in the single-user MCP surface — cooperative, not adversarial; state the consequence: telemetry disciplines buggy producers, not malicious ones) and the HEAD snapshot it was authored against. The intent queue is a write-ahead log yielding an operational-provenance graph (corpus change → intent → agent) distinct from content-provenance (claim → source); it must record not just outcomes but DECISION BASIS sufficient to audit and replay a canonicalization without re-running the LLM (policy/threshold version, dedup similarity score, candidate referents considered, contradiction/trust determinations, the phantom-reconciliation branch taken). Per-producer telemetry (acceptance/rejection/dedup-merge rates, time-in-queue) catches a misbehaving producer at the source.

4. AUTHORSHIP CONTRACT (thin authorship, structured-claim intent). The boundary between agent and librarian is canonical-form authorship, not content. Agents own content: what is true, why it matters, the sources, the framing. The librarian owns form: the canonical page — schema-conformant, citation-grounded, deduped, wikilinked, validated. Agents never produce canonical pages and never carry authorship discipline (page-type schema, citation formatting, dedup lookup, link resolution); that discipline lives in one place, the librarian, so it cannot diverge across the fleet. Chosen over thick intent (agents authoring finished pages) because thick re-imposes derivative authorship on execution agents — the drift and context-pollution the producer-of-intent model removes — and forks the authorship implementation across N agents. Chosen over raw-dump thin intent because that discards structure the agent already paid to produce. Payload richness scales with the agent's unique cognitive value, by page-type: Source intent (URL/ref + extracted claims/quotations with provenance → librarian authors fully); Entity/concept intent (assertions + sources → librarian authors new or merges into existing referent); Synthesis intent (agent's draft reasoning + the question that shaped it + the source set → librarian canonicalizes: grounds every claim to `[[sources/<id>]]`, formats, dedups, links, validates — not re-synthesize from scratch). In all three the agent submits intent payload, never committed pages; canonical-form authoring runs on a worker (parallelized); only commit is serial. MIGRATION DELTA: the current global `wiki-author` flock (`locking.py`) serializes ALL wiki authorship today, not just commit — the agreed N-worker concurrent-authorship model requires narrowing or replacing that lock; flag it.

5. CONCURRENCY & COMMIT PROTOCOL (the panel's highest-risk surface — specify in full). MVCC requires a concrete compare-and-swap, not just "re-validate against HEAD." Specify the per-intent read/write set (target page, dedup-target entity, backlink rows in cited sources). At commit, compare each written page's content-hash / git blob OID at snapshot against current HEAD. Three cases, named: (i) no overlap → commit; (ii) same page, mergeable claims → rebase the structured payload onto current HEAD and re-run the authorship merge step, NOT blind overwrite; (iii) same page, contradictory edit → dead-letter with reason. This must handle concurrent same-entity merges (write-skew): two intents each adding a non-conflicting claim to one entity against the same snapshot must BOTH survive — there is no slug collision to catch a lost update, so it is silent corruption if unhandled. Specify the merge-reattachment protocol when intent resolution merges page B into canonical A, all inside the one commit: rewrite every inbound `[[…B]]` wikilink to A; update bidirectional `wiki_pages:` backlinks in every raw source B cited (drop B, add A) per WIKI.md §5.4; rewrite `synthesizes:`/`## Included works` references; leave a tombstone redirect at B's slug so stable external path-references resolve. The commit gate is idempotent on `intent_id` (re-presenting a committed intent is a no-op returning the prior result). The watched-directory queue provides NO total order; if intent B depends causally on the page intent A creates, intents carry an explicit dependency reference and the committer defers the dependent until its antecedent commits.
