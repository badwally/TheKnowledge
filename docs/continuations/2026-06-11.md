# Continuation — 2026-06-11

## Task for the next session

Resolve the **cross-domain synthesis gap** in the wiki gateway: there is no way to
produce a grounded synthesis page that draws a *balanced* grounding context from —
and is correctly tagged to — **more than one domain**. This surfaced while filing
the data-collectives Stage 2 page, which legitimately cites both `data-collectives`
and `condo-capital-infra` sources but had to be hand-assembled.

This is a gateway design/build task. The data-collectives research project itself
is **complete** (foundation + Stage 2, both grounded into the wiki) — do not reopen
it. This continuation is about the tool limitation it exposed.

## The problem, precisely (verified 2026-06-11, not assumed)

1. **`wiki answer --domain X` hard-excludes every other domain.** Filing the Stage 2
   page with `--domain data-collectives` made the auto-synthesis refuse ("I cannot
   answer this from the provided context") because the condo sources live in
   `condo-capital-infra` and were never retrieved.
2. **Omitting `--domain` retrieves globally, but a single ranked k-window collapses
   toward the lexically-dominant domain.** Evidence (LLM-free `wiki retrieve`, no
   `--domain`):
   - cross-domain query → 2 sections, both `data-collectives`, 0 condo
   - condo-heavy query → returns `condo-capital-infra` (so global retrieval *can*
     reach it)
   - balanced query, k=12 → 3 sections, all `data-collectives`
   So the corpus is reachable, but one call never assembles a *per-domain-balanced*
   context. The model therefore can't synthesize across domains in a single grounded
   call.
3. **`wiki answer` writes single-valued domain frontmatter.** `src/gateway/ops/answer.py:222`:
   `"domains": [domain] if domain else []`. A page spanning two domains cannot be
   tagged to both via the gateway.

Net: the only current way to file a cross-domain grounded page is the manual
**scaffold-then-replace** workaround used twice now (`wiki answer --file` to create
the shell → `wiki edit --section` to install a hand-authored, hand-cited body →
`wiki finalize`). That works but is undiscoverable, error-prone (you hand-map every
`[[sources/<id>]]`), and leaves wrong `domains:` / `sources_count` frontmatter that
must be patched by direct Edit.

## Solution shapes to evaluate (do not prescribe — brainstorm first)

- **`--domains a,b,c` (multi-value) on `wiki retrieve` / `wiki answer`**, with a
  *per-domain quota* merge (retrieve ~k/N per named domain, then merge + re-rank) so
  the grounding block is balanced rather than winner-take-most. Smallest change;
  reuses the existing retrieval ladder.
- **A dedicated `wiki synthesize --domains a,b "<question>"` op** that does
  per-domain retrieval + merge + one grounded call + multi-domain frontmatter, and
  finalizes. Cleaner UX; more surface area.
- **Quota-merge inside the existing global (no-domain) path** so balance is the
  default when no domain is named. Risk: changes default ranking behavior — gated by
  the golden set.
- Independent of the above: make `domains:` frontmatter list-valued from the
  authoring op (fixes point 3 regardless of the retrieval fix).

Recommended starting bias: the multi-value `--domains` + per-domain-quota merge is
the least invasive and directly fixes points 1–2; the list-valued `domains:`
frontmatter fixes point 3. Validate against the golden set before committing any
ranking change.
