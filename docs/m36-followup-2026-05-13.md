## Outstanding M36 converter bugs

Two bug classes surfaced during the `2026-04-29T160943Z` bulk-ingest hand-test
(log at `.knowledge/bulk-ingest-logs/2026-04-29T160943Z.log`).

### `[wikilink-malformed]` — 7 PDFs

**Affected files:**

| PDF filename | log line | unbalanced brackets |
|---|---|---|
| `Cbot - A Six-Part Study Guide To Market Profile.pdf` | 370 | 4 `[[`, 0 `]]` |
| `FallbackPDF__48c7d3ed.pdf` | 1072 | 4 `[[`, 0 `]]` |
| `FallbackPDF__68ddac8b.pdf` | 1316 | 1 `[[`, 0 `]]` |
| `FallbackPDF__dc4baf18.pdf` | 1859 | 0 `[[`, 1 `]]` |
| `FallbackPDF__edf7bd6d.pdf` | 1951 | 0 `[[`, 18 `]]` |
| `Harry D Schultz - Bear Market Investing Strategies.pdf` | 2161 | 1 `[[`, 0 `]]` |
| `LX150Workshop.pdf` | 2435 | 0 `[[`, 8 `]]` |

**Root cause:** `pdfplumber` extracts text verbatim including any `[[` or `]]`
character sequences that appear in the original PDF (e.g. in footnotes, formulas,
table markup). The validator interprets these as malformed wikilinks.

**Fix path:** In `src/gateway/converters/pdf.py`, escape bracket sequences in
the extracted body before returning it from `_extract_pdf()` (line 57) or just
before the `fm.serialize()` call (line 134). Replace literal `[[` with
`[​[` (left bracket + zero-width space + left bracket) and `]]` with
`]​]`. This makes brackets invisible to the wikilink parser without
altering the human-readable text. Alternative: replace with HTML entities
(`&#91;&#91;` / `&#93;&#93;`) if the wiki renderer handles them correctly.

After the fix, re-ingest the 7 affected PDFs:

```bash
wiki ingest <path-to-pdf> --domain <appropriate-domain>
```

### `[source-immutability]` — 4 PDFs (slug hash collision)

**Affected files:**

| PDF filename | log line |
|---|---|
| `FallbackPDF__89eef967.pdf` | 1472 |
| `FEAR.pdf` | 2099 |
| `SSRN-id3953786.pdf` | 2761 |
| `SSRN-id3954600.pdf` | 2765 |

**Root cause:** `_hash_id_from_bytes()` in `src/gateway/converters/pdf.py`
(line 34–36) truncates the SHA-256 digest to **12 hex characters** (48 bits).
With a 396-file corpus, birthday probability of at least one collision is ~0.3%
— these 4 files hit it. The collision causes a second PDF to resolve to an ID
already occupied by a different file, and the immutability guard correctly
rejects the write.

```python
# current — 12-char / 48-bit prefix
def _hash_id_from_bytes(data: bytes, max_chars: int = 12) -> str:
    digest = hashlib.sha256(data).hexdigest()[:max_chars]
    return f"pdf-{digest}"
```

**Fix path:** Widen `max_chars` from `12` to `20` (80 bits). At 80-bit prefix
the birthday collision probability over a 10,000-file corpus is ~4 × 10⁻¹⁰ —
effectively zero for any realistic personal knowledge base.

```python
def _hash_id_from_bytes(data: bytes, max_chars: int = 20) -> str:
```

The change is backward-compatible: existing IDs are unaffected (they retain
their 12-char slugs). Only new fallback-hash IDs generated after the change
will use 20 chars. After the fix, re-ingest the 4 collision PDFs with fresh
unique IDs.
