## What shipped

### K1 — Gateway edit-path

- **Validator line-number fix** per D2. New `frontmatter.body_line_offset(text)`
  helper. `validate_wiki_page` and `validate_citation_grounding` gained
  `body_line_offset: int = 0` (default preserves back-compat for tests
  + lint). Three production callers (`apply_plan`, `finalize`,
  `lint/schema_drift`) updated to pass the offset so their error
  messages are now file-relative (matching `wiki cite` numbering).
- **New `wiki cite-add` op** at `src/gateway/ops/cite_add.py` implementing
  the escalation pipeline per D5:
  1. **Exact** substring match in body
  2. **Normalized** substring (NFKC + casefold + collapse internal
     whitespace + tolerate trailing punctuation)
  3. **Fuzzy** (LLM-judged) — opt-in via `--fuzzy` flag, off by default
  4. **Not-found** → error with 3 nearest-by-edit-distance suggestions
  At any step: 1 hit → cite via underlying `cite()` op (inherits
  bidirectional backlinks + atomic write + log append); 2+ hits →
  ambiguity error with file-relative line numbers and tiebreaker hint.
  Idempotency built in: a re-cite of the same claim with the same
  source returns `no_op=True`.
- **New `wiki edit --section <name>` op** at
  `src/gateway/ops/edit_section.py`. Constrained: replaces only the
  body of one named `## Section` (case-insensitive header match);
  frontmatter and other sections stay untouched. Re-runs full
  validator on the result and rejects if the page would no longer
  satisfy schema or citations. Acquires `file_lock("wiki-author")`
  around the write.
- **CLI subcommands** `wiki cite-add` and `wiki edit` added; both in
  `IMPLEMENTED`. `cite-add` argparse: `<page> <claim> <source-id>
  [--fuzzy]`. `edit` argparse: `<page> --section <name> --body-file
  <path>` (or stdin).
- **MCP wrappers** `wiki_cite_add` and `wiki_edit` added to
  `mcp_server.py`. The K2 parity test from wave-1 went red the moment
  `cite-add`/`edit` landed in `IMPLEMENTED`; adding the wrappers brought
  it back green — exactly the forcing-function dynamic the plan called
  out.

### K4 — Scheduler substrate

- **New `croniter>=2.0` dependency** in `pyproject.toml`.
- **New `src/gateway/scheduler.py`** module:
  - `ScheduleJob` dataclass: `name`, `cron`, `command`, `enabled`,
    `cooldown_seconds`, `last_run`, `last_exit_code`,
    `last_duration_seconds`.
  - `load_schedule()` / `save_schedule()` round-trip
    `.knowledge/schedule.yaml`.
  - `is_job_due(job, now)` uses `croniter`; respects disabled flag and
    cooldown guard (jobs that failed in the last
    `cooldown_seconds` are skipped to prevent launchd-restart
    thrashing).
  - `run_job(job)` subprocess shell-out (not in-process op dispatch)
    so any command is schedulable, not just `wiki *`. Uses
    `cwd=KB_ROOT`, captures stderr tail for diagnostics, 1-hour hard
    timeout per job.
  - `run_all_due(dry_run=False)` ticks the schedule; per-job
    `file_lock("schedule-<name>")` prevents overlapping ticks from
    double-executing.
- **CLI `wiki schedule` subcommand** with seven sub-actions:
  `list`, `add`, `remove`, `enable`, `disable`, `run`, `dry-run`. `run`
  is what launchd fires every 60s. Cron validation runs at `add` time
  via `croniter`.
- **`scripts/install_scheduler.sh`** mirrors `install_watcher.sh`:
  generates `~/Library/LaunchAgents/com.knowledge.scheduler.plist`
  with `StartInterval=60`, `RunAtLoad=true`, logs to
  `.knowledge/scheduler.{out,err}.log`. **Not auto-installed** —
  you run it when ready.
- **Scheduler is CLI-only** per C4 spirit. Added to
  `mcp_server.CLI_ONLY` with an inline comment explaining the
  reasoning: agents must not be able to grant themselves persistent
  shell-command execution. The parity test pins this decision.
- **UTC-only in v1.** Documented in scheduler module docstring.

### K3 — Cloud shim

- **New `src/gateway/web/auth.py`** for bearer-token auth.
  Tokens stored as sha256 hashes in `.knowledge/auth.yaml`; plaintext
  printed once at `wiki auth add` time. Verification uses
  `hmac.compare_digest` for constant-time comparison. `verify_bearer`
  FastAPI dependency raises `HTTPException(401)` on missing/invalid;
  returns the token name on success (audit-friendly). `last_used_at`
  timestamp updated on successful auth.
- **New `src/gateway/web/routes/cloud.py`** with `POST /api/ingest`
  per D4. Sync via TaskStore (mirror of `/api/ops/ingest` pattern),
  returns 202 + task_id, poll via existing `/api/tasks/{id}`.
  Accepts JSON `{"url", "domain"?, "draft"?, "with_plan"?}` OR
  multipart form (`file`, plus same optional fields). Bearer-token
  guarded via FastAPI dependency. Cloud-ingest events appended to
  `log.md` with the token name (not the secret) for audit trail.
- **`wiki auth` CLI subcommand** (`add`/`list`/`revoke`). `add` mints
  via `secrets.token_urlsafe(32)`, persists the sha256 hash, prints
  the plaintext **once**. `list` shows names + timestamps (no hash
  disclosure). `revoke` removes by name. CLI-only per C4 (added to
  `mcp_server.CLI_ONLY`) — agents must not mint or revoke their own
  bearer tokens.
- **`.gitignore` additions** for `.knowledge/auth.yaml` and
  `.knowledge/scheduler.*` (defense-in-depth — the parent
  `.knowledge/` is already gitignored from M1, but tokens deserve
  belt-and-suspenders).
- **iOS Shortcut sub-deliverable** (D6 amendment):
  - `TUTORIAL.md § 8a "Remote capture from iOS (Tailscale + Shortcuts)"`
    — full step-by-step build doc with Share Sheet trigger config,
    HTTP action body shape, Show Notification on success, export
    instructions.
  - `scripts/test-ingest-curl.sh` — curl invocation matching the
    Shortcut's HTTP call exactly. Configurable via `WIKI_URL` and
    `WIKI_TOKEN` env vars so it can target either localhost during
    desktop testing or the tailnet hostname for remote validation.
  - **`scripts/wiki-capture.shortcut`** — deferred to Andrew per D6.
    Build the Shortcut on the iPhone following the TUTORIAL, export
    to `scripts/`, commit. Anyone cloning the repo can then one-tap
    import on iOS.
